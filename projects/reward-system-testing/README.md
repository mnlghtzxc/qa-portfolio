# Reward System Testing

# Тестирование модуля квестов в мобильной игре

Исследовал модуль ежедневных и еженедельных заданий в условно-бесплатной мобильной игре. Модуль завязан на прогресс игрока, награды, таймеры и синхронизацию с сервером. Основная цель — найти уязвимости, которые могут сломать игровую экономику или вызвать рассинхрон.

## С чего начал
Разобрал главный экран и сам модуль на составляющие: прогресс-бар, карточки квестов, таймеры, кнопки получения наград, переходы между состояниями. Понял, что клиент отвечает только за отображение, а сервер — за всю логику: валидацию условий, начисление наград, защиту от повторов. Граница ответственности чёткая, и это сразу дало вектор для проверок: все манипуляции с клиентом (мультитапы, обрывы связи, подмену локальных данных) не должны влиять на серверное состояние.

## Примеры тест-кейсов (из 15 составленных)

**1. Начисление награды после 100% прогресса**
- Шаги: выполнить действия по условию квеста до заполнения прогресс-бара на 100%, нажать кнопку «Получить награду».
- Ожидаемый результат: награда зачисляется на баланс, статус квеста меняется на «Награда получена», прогресс-бар обновляется.
- Приоритет: высокий.

**2. Защита от мультитапа при получении награды**
- Шаги: довести квест до статуса «Награда доступна», быстро несколько раз нажать кнопку «Получить».
- Ожидаемый результат: награда начисляется ровно один раз, баланс увеличивается на корректную сумму, повторные запросы игнорируются.
- Приоритет: высокий (критично для экономики).

**3. Синхронизация таймера после реконнекта**
- Шаги: начать квест с активным таймером, включить авиарежим на 30 секунд, восстановить сеть и вернуться в модуль квестов.
- Ожидаемый результат: таймер показывает оставшееся время с учётом прошедшего, не сброшен и не перезапущен.
- Приоритет: высокий.

## Примеры найденных багов

**1. Повторное начисление награды при быстром двойном тапе**
- Серьёзность: Критическая
- Шаги: Довести квест до 100%, дождаться статуса «Награда доступна», максимально быстро нажать кнопку «Получить» два раза.
- Ожидаемый результат: Награда начисляется один раз, повторный запрос блокируется.
- Фактический результат: Награда начисляется дважды — баланс увеличивается на удвоенную сумму.
- Причина: Отсутствует идемпотентность запроса получения награды. Сервер не проверяет, не была ли награда уже выдана по этому квесту.

**2. Прогресс-бар показывает 100%, но кнопка «Получить» не появляется**
- Серьёзность: Высокая
- Шаги: Выполнить условия квеста точно до 100%, перейти в модуль квестов.
- Ожидаемый результат: Статус меняется на «Награда доступна», кнопка активна.
- Фактический результат: Прогресс-бар заполнен, но статус остаётся «В процессе выполнения», кнопка недоступна.
- Причина: Расcинхронизация статуса между клиентом и сервером. Сервер засчитал последнее действие, но не отправил событие смены статуса.

**3. Таймер квеста сбрасывается при переводе системных часов назад**
- Серьёзность: Высокая
- Шаги: Дождаться, когда до завершения таймера останется ~5 минут, перевести системное время на 1 час назад, вернуться в модуль квестов.
- Ожидаемый результат: Таймер продолжает корректный отсчёт от серверного времени.
- Фактический результат: Таймер сбрасывается до исходного значения, время до новых квестов увеличивается.
- Причина: Клиент использует локальное время устройства для расчёта оставшегося времени вместо серверного.

**4. Потеря награды при обрыве соединения в момент получения**
- Серьёзность: Критическая
- Шаги: Довести квест до статуса «Награда доступна», нажать «Получить» и мгновенно включить авиарежим.
- Ожидаемый результат: При восстановлении сети награда либо зачислена, либо квест остаётся в статусе «Награда доступна».
- Фактический результат: Квест переходит в статус «Награда получена», но баланс не изменяется — награда потеряна.
- Причина: Клиент оптимистично меняет статус до подтверждения от сервера. Серверный ответ теряется при обрыве, компенсация отсутствует.

**5. Отрицательное значение валюты при отмене награды**
- Серьёзность: Средняя
- Шаги: Получить награду за квест, затем административно отменить выдачу через серверные инструменты.
- Ожидаемый результат: Баланс корректно уменьшается, но не уходит в минус (проверка на достаточность средств).
- Фактический результат: Баланс становится отрицательным, UI подсвечивает некорректное значение.
- Причина: Отсутствует проверка на отрицательный баланс при серверной отмене операции.

## Самые критичные риски, которые выделил
- Дублирование награды из-за повторного запроса — прямой удар по экономике.
- Расcинхронизация статуса квеста: игрок видит кнопку «Получить», но сервер считает, что награда уже выдана.
- Некорректная замена квестов по таймеру — можно случайно дать игроку фармить задания быстрее задуманного.
- Потеря награды при обрыве сети — без гарантированной доставки игрок остаётся ни с чем.

## Что в итоге
Составил план тестирования (функциональное, UI/UX, производительность, стресс-тесты соединения), написал 15 тест-кейсов на ключевые сценарии, выделил кандидатов для автоматизации (smoke-проверки получения наград, прогресса, таймеров). Проект помог прокачать системный взгляд на клиент-серверное взаимодействие: всегда проверять, кто хозяин состояния, и не доверять клиенту.
