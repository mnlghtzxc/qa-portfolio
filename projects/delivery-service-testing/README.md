# Delivery Service Testing

# Тестирование коммерческого сервиса аренды самокатов

Проект по тестированию веб-приложения для заказа самокатов с формой оформления, экраном статуса заказа и набором API для курьеров и отслеживания. Проверял фронтенд (валидацию, вёрстку, бизнес-логику) и бэкенд (контракты API, работа с БД).

## Инструменты
- DevTools (Network) — подмена ответов сервера, проверка отображения статусов.
- Postman — запросы к API, анализ response.
- Charles — перехват и модификация трафика с мобильного эмулятора для проверки edge-кейсов.
- SQL (PostgreSQL) — проверка целостности данных после операций (например, убедился, что отменённый заказ действительно удаляется из БД, а не только исчезает из UI).
- Браузеры: Google Chrome и Яндекс.Браузер (сравнение поведения).

## Фронтенд

**Экран «Статус заказа»**
- Проверил цепочку статусов и активность кнопки «Отменить заказ». По требованиям кнопка должна быть активна только на первом статусе («Самокат на складе»), но оказалась кликабельна на всех — критичный баг, позволяющий отменить уже выполняемый заказ.
- Поиск заказа: ошибка «Такого заказа нет» при вводе несуществующего номера, корректное отображение данных после поиска.
- Длинные значения в полях (имя, адрес, комментарий) — вёрстка ломалась, текст наезжал на соседние блоки или обрезался.

**Экран «Сделать заказ» — валидация полей**
Использовал классы эквивалентности и граничные значения. Основные находки:
- Поле «Имя» не принимало дефис, хотя требования разрешали (например, «Анна-Мария»).
- Поле «Адрес» пропускало строки короче 5 символов и игнорировало верхнюю границу в 50 символов.
- Поле «Телефон» с префиксом «+» позволяло ввести номер короче 12 символов; без «+» — не проходили номера длиной 12 символов.
- «Дата доставки» позволяла выбрать прошедшую дату и оставить поле пустым.
- «Комментарий»: ограничение 24 символа не работало, пропускало до 50 символов, включая латиницу и спецсимволы, которые по требованиям были запрещены.

## Бэкенд (API)
- **Создание курьера (POST /api/v1/courier)**: проверял поля login, password, firstName. Сервер возвращал 201 на невалидные символы и длину — валидация оказалась слабее заявленной.
- **Удаление курьера (DELETE)**: при успешном удалении курьера связанные заказы из БД не удалялись, что нарушало целостность данных. Также запрос без id давал неинформативный ответ вместо 400.
- **Получение заказа по треку (GET)**: работало согласно спецификации.

## Чему научился
- Сопоставлять поведение фронтенда с реальными ответами сервера через подмену в DevTools.
- Проверять идемпотентность и атомарность API-операций (особенно важных для списаний и отмен).
- Видеть нестыковки контракта: если документация говорит, что поле обязательное, а сервер его пропускает — это баг.
- Использовать SQL для проверки данных после операций — усилило доказательную базу баг-репортов.
