# Комплексное тестирование сервиса доставки: веб, API и мобильное приложение

## 🎯 Цель
Показать системный подход к тестированию коммерческого продукта: фронтенд (валидация, бизнес-логика, вёрстка), бэкенд (REST API, контракты), мобильное приложение курьера и проверки целостности данных через SQL.

## 🧠 Ключевые навыки
- Декомпозиция пользовательских сценариев: клиент (веб) → курьер (mobile) → система (API + БД)
- Тестирование вёрстки, валидации полей и бизнес-логики на фронтенде
- Проверка контрактов REST API: статус-коды, структура ответов, обработка ошибок
- Мобильное тестирование (Android): авторизация, офлайн-режим, нотификации, портретная ориентация
- Анализ целостности данных: SQL-запросы после критических операций (удаление курьера, отмена заказа)
- Кросс-браузерное тестирование (Chrome, Яндекс.Браузер) и работа с логами эмулятора
- Написание чек-листов, тест-кейсов, матриц валидации и баг-репортов

## 🛠️ Инструменты
- **DevTools** (Network, подмена ответов)
- **Charles Proxy** (перехват и анализ мобильного трафика)
- **Postman** (ручное тестирование API)
- **SQL** (PostgreSQL, проверка целостности данных)
- **Android Studio** (эмулятор, логи)
- **YouTrack** (баг-трекинг)
- **Тестовое окружение:** веб-приложение заказа самокатов, мобильное приложение курьера (`scooter-v2.0.apk`), REST API

## 📦 Что тестируем
- **Веб-приложение** заказа самокатов: экран оформления, статус заказа.
- **Мобильное приложение курьера** (Android): авторизация, список заказов, принятие/завершение, нотификации, офлайн-режим.
- **API**: создание/удаление курьера, получение заказа по треку.
- **База данных**: PostgreSQL, проверка корректности удаления/обновления данных.

## 🧪 Особенности тест-дизайна
- **Декомпозиция на пользовательские сценарии**: заказчик (веб) → курьер (мобильное) → система (API+БД).
- **Классы эквивалентности и граничные значения** для каждого поля ввода (подробная матрица валидации).
- **Проверка контрактов API**: сопоставление документации, реального поведения и кодов ошибок.
- **Анализ целостности данных**: SQL-запросы после критических операций (удаление курьера, отмена заказа).
- **Кросс-браузерное тестирование**: Google Chrome, Яндекс.Браузер.
- **Тестирование нотификаций и офлайн-режима**: уведомления за 2 часа до конца аренды, работа без сети, блокировка экрана.

|---------|---------------------------------------------------------------|-------------|--------------|
| MV8-78  | Кнопка «Отменить заказ» активна на всех статусах               | Critical    | Тестирование статусных моделей: права на операцию должны проверяться сервером, а не только скрытием кнопки на фронте |
| MV8-139 | DELETE /api/v1/courier не удаляет связанные заказы             | High        | Каскадное удаление — критичный контракт БД. Всегда проверять, что FOREIGN KEY и CASCADE настроены правильно |
| MV8-121 | POST /api/v1/courier создаёт курьера с кириллицей в логине    | High        | Серверная валидация должна быть зеркальна клиентской — иначе данные, недопустимые в UI, просачиваются через API |
| MV8-104 | Отменённый заказ не удаляется из списка после pull-to-refresh  | High        | Pull-to-refresh не гарантирует консистентность данных — всегда проверять состояние после обновления UI |
| MV8-106 | Карточка заказа не переключается в полную версию тапом         | Medium      | Проверять не только наличие обработчика, но и область касания (hit area), особенно на мобильных устройствах |
| MV8-129 | Длинное имя курьера ломает вёрстку на экране статуса           | Medium      | Тестировать верстку экстремальными длинами — не только границы валидации, но и визуальное отображение |
| MV8-107 | Некорректное сообщение при попытке принять чужой заказ          | High        | Проверять не только позитивный сценарий, но и понятность ошибок для пользователя |
| MV8-113 | Приложение переходит в альбомную ориентацию                    | Medium      | Тестирование ориентации — обязательная часть мобильных проверок |

## 🧪 Как я применяю это в тестировании
1. **Сквозной сценарий «Заказ → Доставка»:** проверяю, что созданный на вебе заказ появляется у курьера, проходит все статусы и корректно завершается. Отслеживаю соответствие статусов в UI, ответах API и записях в БД.
2. **Тестирование прав доступа:** удостоверяюсь, что курьер не может взять чужой заказ или отменить заказ в статусе «Выполнен». Баг MV8-78 — классический пример, когда фронтенд маскирует проблему, а прямое обращение к API её вскрывает.
3. **Проверка целостности данных:** после удаления курьера через API выполняю SQL-запрос, чтобы убедиться, что его заказы тоже удалены. Если нет (MV8-139), это сразу стоп-релиз.
4. **Тестирование обработки ошибок:** через Charles подменяю ответы сервера (ошибки 5xx, медленный ответ) и проверяю, как мобильное приложение показывает ошибки — не падает ли, предлагает ли повторить запрос.
5. **Нотификации и фоновая работа:** проверяю, что уведомление приходит ровно за 2 часа до конца аренды (MV8-111), приходит даже при заблокированном экране и без интернета, и не приходит, если уведомления запрещены.
