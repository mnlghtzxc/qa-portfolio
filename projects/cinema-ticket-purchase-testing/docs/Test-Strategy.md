# Test Strategy — Cinema Ticket Purchase API

## 1. Цель
Обеспечить уверенность в корректной работе REST API для кинотеатра: соответствие бизнес-правилам, целостность данных, отказоустойчивость при некорректных входных данных.

## 2. Объект тестирования
- **API:** 12 эндпоинтов (клиентские + административные), базовый URL: `http://localhost:5000/api/v1`.
- **База данных:** PostgreSQL (6 таблиц), ограничения целостности (CHECK, UNIQUE, частичный индекс).
- **Окружение:** Docker (docker-compose), Flask-приложение.

## 3. Уровни тестирования

### Уровень 1: Smoke
- **Цель:** быстро убедиться, что сервер жив и ключевые эндпоинты отвечают.
- **Инструмент:** bash-скрипт `smoke.sh`.
- **Запуск:** вручную или автоматически через GitHub Actions при каждом push.

### Уровень 2: Ручное тестирование API
- **Цель:** проверить функциональность, контракты (формат ответов, статус-коды), бизнес-правила.
- **Инструмент:** коллекция Postman (21 запрос с тестами).
- **Покрытие:** позитивные и негативные сценарии, проверка обязательных полей, типов данных, кодов ошибок.

### Уровень 3: Проверка целостности данных
- **Цель:** убедиться, что данные в БД не нарушают бизнес-правила после операций API.
- **Инструмент:** SQL-запросы вручную (`sql/checks.sql`).
- **Покрытие:** перепродажа билетов, несоответствие статусов и времени сеансов, орфанные записи, уникальность email, пересечение сеансов.

### Уровень 4: CI/CD (автоматическая проверка)
- **Цель:** гарантировать, что при каждом изменении кода основные эндпоинты остаются работоспособными.
- **Инструмент:** GitHub Actions (workflow `smoke.yml`).
- **Что делает:** поднимает Docker-окружение, загружает тестовые данные, запускает `smoke.sh`.

## 4. Что НЕ тестируется (осознанные ограничения)
- **Нагрузочное тестирование:** не проводится, т.к. API учебное и не предназначено для production-нагрузок.
- **Безопасность:** не проверяется, т.к. нет аутентификации и чувствительных данных.
- **Кросс-браузерное / UI тестирование:** отсутствует фронтенд.
- **Фильтрация по дате и movie_id:** параметры заявлены в документации, но не реализованы в коде.

## 5. Инструменты
| Инструмент | Назначение |
|---|---|
| Postman | Ручное тестирование API, проверка контрактов |
| curl + bash | Smoke-проверки, быстрый прогон |
| PostgreSQL (psql) | Проверка целостности данных |
| Git + GitHub | Контроль версий, CI/CD |
| Docker Compose | Управление тестовым окружением |

## 6. Окружение
- **Локальное:** WSL2 (Ubuntu), Docker Desktop.
- **CI:** GitHub-hosted runner (ubuntu-latest).

- Все SQL-запросы из `checks.sql` возвращают 0 строк (нет аномалий).
- Все 21 тест в коллекции Postman проходят успешно (All Green) на чистом окружении.
