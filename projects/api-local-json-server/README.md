# Тестирование REST API: кастомная серверная валидация и автоматизация в Postman

## 🎯 Цель
Показать умение проектировать тесты API: позитивные/негативные сценарии CRUD, автоматические проверки в Postman, тестирование серверной валидации и документирование результатов.

## 🧠 Ключевые навыки
- Разработка структурированных коллекций Postman с переменными окружения
- Проектирование позитивных и негативных тест-кейсов для CRUD-операций
- Автоматическая валидация статус-кодов, Content-Type и структуры JSON
- Тестирование кастомной серверной валидации (типы данных, граничные значения)
- E2E-цепочки с передачей `id` через переменные для изоляции данных
- Документирование найденных багов с анализом причин

## 🛠️ Инструменты
- **Postman** (коллекции, переменные окружения, pre-request/post-response скрипты)
- **Node.js** (json-server)
- **JavaScript** (кастомная серверная валидация в `server.js`)
- **Тестовое окружение:** локальный json-server

## 📦 Что тестируем
REST API локального json-server, расширенного кастомной валидацией (`server.js`).  
**Сущность `Post`:**
| Поле    | Тип    | Обязательное | Доп. ограничения              |
|---------|--------|--------------|-------------------------------|
| id      | number | авто         | —                             |
| title   | string | да           | не пустая строка, не пробелы   |
| body    | string | да           | не пустая строка, не пробелы   |
| userId  | number | да           | целое, положительное           |

## 🧪 Особенности тест-дизайна
- **Полный E2E CRUD-сценарий**: POST → GET → PUT → PATCH → DELETE с передачей `id` через переменную окружения `currentPostId`
- **Изоляция данных**: каждый прогон создаёт новый пост и удаляет его в конце — никакого мусора
- **Проверка контракта ошибок**: все негативные тесты валидируют `message` и/или `errors` в теле ответа
- **Верификация Content-Type**: каждый позитивный тест проверяет `application/json; charset=utf-8`

## 🤖 Автоматические проверки (в каждом тесте)
`pm.test()` — статус-код, Content-Type, тело ответа (структура, типы, значения), сообщения об ошибках.

## 🧪 Как я применяю это в тестировании
1. **Регресс перед релизом:** запускаю Collection Runner и за минуту убеждаюсь, что все CRUD-операции и серверная валидация работают как ожидалось.
2. **Проверка контракта API:** если разработчик изменит текст ошибки или структуру ответа, мои тесты это сразу обнаружат.
3. **Изоляция дефекта:** если падает E2E-тест, я сразу вижу, на каком шаге (POST, PUT, PATCH, DELETE) произошёл сбой, и локализую проблему.
4. **Живая документация:** коллекция служит исполняемой спецификацией — как API должно обрабатывать ошибки и валидировать входящие данные.

## 🐞 Найденные баги
| ID      | Описание                              | Серьёзность | Статус     | Чему научил |
|---------|---------------------------------------|-------------|------------|--------------|
| BUG-001 | id сохранялся как строка в db.json    | Medium      | Исправлено | Важность строгой типизации: строка `"1"` ≠ число `1`, что ломало сравнение идентификаторов |
| BUG-002 | DELETE возвращает 200 вместо 204      | Minor       | Известная особенность json-server | Знание спецификаций (RFC) помогает отличить реальный баг от особенности фреймворка |
